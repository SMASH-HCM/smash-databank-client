# Cohorts, baselines, indices and landmarks

A **cohort** is a set of patients defined upstream, for example FLORENCE Training or RENNES Test. Membership determines who is exported. Selecting a cohort does not create a new random split, change the clinical baseline or establish eligibility for every endpoint.

An **index** is the prediction point for a model input. In the standard client this is the patient's **clinical baseline** from the embedded `smash_endpoint_censor.baseline_date` and `baseline_age` ledger. A **landmark** is another name for a prediction index, particularly when a patient can have several prediction times. These are clinical time coordinates, not CSV row numbers, DataFrame indices or database indexes.

## The standard client: one fixed baseline per patient

Suppose a patient has baseline 1 January 2020 and recorded baseline age 50:

```text
prior history                    baseline                    follow-up
2019-01-01 -------------------- 2020-01-01 ------------------ 2022-01-01
                              prediction index
```

- **Snapshot (default):** only eligible observations on 1 January 2020. One row per cohort patient; no earlier value is carried forward.
- **Latest history, 730 days:** latest eligible value between baseline minus 730 days and baseline, inclusive. The prediction index is still 1 January 2020. Optional previous-value/count/mean columns describe observations in that window.
- **Baseline event scope:** dated input events on/before that same baseline, with an optional history window and availability mask. It retains many rows per patient.
- **Full-history events:** may include follow-up after baseline. These must be cut off before use as baseline prediction inputs.

The default availability policy places prediction **after diagnostic assessment and before new treatment decisions**. Same-day eligible measurements can enter; new therapeutic decisions, administrative/outcome-derived facts and unclassified same-day roles are held. Date-only records cannot establish true intraday order. `strict-before` is an explicit historical boundary comparison; it excludes day zero and does not itself solve all source-role leakage. See [BASELINE_AVAILABILITY.md](BASELINE_AVAILABILITY.md).

Every selected patient must have one valid baseline date/age pair. Missing, invalid or duplicate anchors block the full baseline export. Cohort membership dates, first measurements and earliest visits are not substituted. FLORENCE source calendar dates may be synthetic coordinates: interpret elapsed intervals and recorded ages using the release's date policy, rather than assuming the calendar year is a real-world date.

Standard tabular outputs have `person_id`, `site`, `cohort`, `snapshot_date`, and clinical feature columns. `samples.csv` in the companion directory contains `landmark_id = <person_id>:baseline`, baseline date and age. This is one fixed input row, without endpoint-specific outcome labels or annual indices. Baseline age is normally a companion field; `esc-risk` or a saved set with `anchor_features: ["baseline_age_years"]` explicitly adds it as a feature.

## A history window is different from an outcome horizon

| Term | Example | Which side of prediction? |
|---|---|---|
| Lookback/window | Use inputs observed in the previous 730 days | Before/on baseline, subject to availability |
| Prediction index | 1 January 2020, recorded age 50 | Boundary between inputs and future |
| Outcome horizon | Predict an endpoint in the next two years | After baseline |
| Censoring | Follow-up ends before the horizon | Determines whether an outcome can be assessed |

`--lookback-days 730` configures **inputs only**. It does not request a two-year label. For a future supervised task, a patient censored six months after baseline cannot automatically be labelled event-free at two years. Endpoint-specific prevalence, ascertainment, censoring and at-risk eligibility must be reviewed before producing labels. The standard client intentionally exports features without inventing these decisions.

## Repeated/annual landmarks: historical experiment tools

The retained `smash_hcm_databank_client.legacy.build_rolling_landmarks` module consumes prepared CSV contracts and implements an older experiment policy: training patients may have baseline plus eligible annual anniversaries, while held-out TEST patients use their fixed baseline only. It writes endpoint-specific `landmarks.csv`, `landmark_horizon_labels.csv` and `landmark_audit.json`. These are **not generated by standard `export` or by enabling history features**. See the [historical methodology](EXPORT_METHODOLOGY.md#study-landmarks-and-outcome-labels) before using them.

For example, a training patient's indices at ages 50, 51 and 52 are three correlated samples from the same person. At each index, truncate inputs again, reassess whether the patient is still at risk, and measure the outcome horizon from that index. A later event must not appear in earlier inputs. Keep all indices for a person in one split, use patient-grouped validation, and account for repeated sampling; the legacy policy weights eligible samples inversely by that patient's endpoint-specific landmark count. Never split those rows randomly across train/test or collapse different endpoint landmarks into one label.

The patient report's **training-index count** comes only from a recognized explicit ledger. If absent it is unknown, not zero and not an inferred annual count. Merely having cohort/anchor/endpoint ledgers does not establish a validated repeated-landmark policy for a new release.
